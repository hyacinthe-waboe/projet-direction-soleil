1 - Approche Logique 


1.1. Schéma Relationnel


A partir du modèle conceptuel de données proposé par le client, nous avons élaboré le modèle logique de données ci-dessous :


CLIENTS(CodeC, NomC, PrénomC, TelC, MelC)
AEROPORTS_DEP(CodeA, NomA)
CIRCUITS(CodeCI, NomCI, PrixBase,NbPersMax, #CodeCI_Est_Complete)
PAYS(CodeP, NomP, AvisGen)
SITES(CodeS, NomS, TypeS, DescripS)
ANIMATIONS(CodeAN, NomAN, TypeAN, HeureDeb, JourSemaine, #CodeH)
HOTELS(CodeH, NomH, Categorie, VilleH, TelH, MelH)
GUIDES(CodeG, NomG, PrenomG, DatePremier)
ZONE_GEO(CodeZ, ZoneGeo)
ACTIVITE(CodeAC, NomAC, TarifAC)
LANGUE(CodeL, NomL)
MOIS(CodeMois, LibelleMois)
CHOIX ( #CodeC, #CodeA, #CodeCI, DateDepartC, OrdrePreference )
RESERVER (  #CodeC, #CodeA, #CodeCI, DateDepartR, DateResa, NbPers )
MAJORATION ( #CodeA, #CodeCI,  DateDepartM, MontantMaj)
PRATIQUER ( #CodeG, #CodeL, NiveauL )
VALIDITE ( #CodeAC, DateDebut, DateFin ) 
REALISER ( #CodeCI, #CodeAC, DateDepartRe, JourSem )
LOGER ( #CodeCI, #CodeH, JourSe ) 
VISITER ( #CodeCI, #CodeS, JourSe2, HeureVisite, DureeVisite )
AVIS ( #CodeP, #CodeMois, TempMin, TempMax, AvisMens, TempMinMoy, TempMaxMoy )
SITUER ( #CodeCI, #CodeZ, #CodeP ) 
ACCOMPAGNER ( #CodeG, #CodeCI, DateDepartA)
________________
1.2. Commentaires


Lors de l’élaboration du modèle relationnel, on s’est aperçu de quelques modifications indispensables pour garantir le bon fonctionnement de la base de données :
* Un changement des noms des attributs “Date” données sur le dictionnaire de données était nécessaire. Pour éviter toute ambiguïté avec le type de données DATE sous Oracle, nous avons renommé les attributs concernés. Donc pour la relation Reserver par exemple, au lieu de mettre “Date” comme nom, nous avons plutôt défini “DateDepartR”. Les noms d’attributs choisis sont : DateDepartC, DateDepartM, DateDepartA, DateDepartRe.
* Tous les noms des relations ont été définis en majuscules.
* Tous les attributs ou tables ayant des accents ont été écrits sans accents.

2.1.9. Requête 9


Énoncé : Donner les noms des circuits disponibles au départ de Toulouse qui permettent de visiter tous les sites de Tunisie.


Requête SQL :
SELECT DISTINCT c.NomCI
FROM circuits c, majoration m, aeroports_dep a, situer s, pays p
WHERE c.CodeCI = m.CodeCI
AND m.CodeA = a.CodeA
AND c.CodeCI = s.CodeCI
AND s.CodeP = p.CodeP
AND LOWER(a.NomA) = 'toulouse'
AND LOWER(p.NomP) = 'tunisie'
AND m.datedepartm NOT IN (
   SELECT r.dateDepartR
   FROM reserver r
   WHERE r.CodeCI = c.CodeCI
   GROUP BY r.dateDepartR
   HAVING SUM(r.NbPers) >= c.NbPersMax
)
AND NOT EXISTS (
   SELECT 1
   FROM situer s2, visiter v
   WHERE s2.CodeCI = v.CodeCI
   AND s2.CodeP = p.CodeP
   AND NOT EXISTS (
       SELECT 1
       FROM visiter v2
       WHERE v2.CodeCI = c.CodeCI
       AND v2.CodeS = v.CodeS
   )
);
Résultat : 


  

Figure 9: Résultat de la requête 9 sur SQL Developer
Justification :


La requête  est une division relationnelle : on cherche les circuits, partant de Toulouse, qui visitent tous les sites tunisiens. SQL n’a pas de quantificateur "pour tout", donc on le remplace par une double négation équivalente. Ainsi, "le circuit visite tous les sites tunisiens" revient à dire "il n’existe aucun site tunisien que le circuit ne visite pas".


Le NOT EXISTS extérieur parcourt les sites tunisiens (ceux visités par un circuit situé en Tunisie). Le NOT EXISTS intérieur vérifie, pour chacun, si le circuit le visite. Un seul site manqué élimine le circuit. La condition NOT IN permet ensuite d'exclure les dates où le circuit est complet, en tenant compte des réservations de tous les aéroports, tout en sélectionnant uniquement les départs proposés depuis Toulouse.


Le résultat est "Perles de Tunisie". Les sites tunisiens sont les sites 1 à 7. Seul ce circuit les visite tous, alors que les quatre autres circuits tunisiens en manquent au moins un. Ce résultat correspond bien à la définition de l'énoncé.

2.2. Requêtes SQL Supplémentaires
2.2.1. Chiffre d'affaires total par départ
Énoncé : Pour chaque départ ayant au moins une réservation, donner le nom du circuit, l'aéroport, la date, le nombre total de voyageurs inscrits et le chiffre d'affaires total généré. Le chiffre d'affaires est calculé à partir du nombre de personnes réservées, multiplié par la somme du prix de base et de la majoration. Classer les résultats par chiffre d'affaires décroissant.


Utilité métier : Comparer les départs selon leur chiffre d'affaires afin d'identifier ceux qui génèrent le plus de revenus pour l'agence.


Requête SQL :
SELECT CI.NomCI, A.NomA, R.DateDepartR, SUM(R.NbPers) AS TotalVoyageurs,
       SUM(R.NbPers * (CI.PrixBase + M.MontantMaj)) AS ChiffreAffaires
FROM CIRCUITS CI, AEROPORTS_DEP A, MAJORATION M, Reserver R
WHERE CI.CodeCI = R.CodeCI
AND A.CodeA = R.CodeA
AND M.CodeCI = R.CodeCI
AND M.CodeA = R.CodeA
AND M.DateDepartM = R.DateDepartR
GROUP BY CI.CodeCI, CI.NomCI, A.CodeA, A.NomA, R.DateDepartR
ORDER BY ChiffreAffaires DESC;
Résultat : 
  
…  
Figure 11: Résultat de la requête supplémentaire 1 sur SQL Developer


Justification :


La requête permet de calculer le nombre total de voyageurs et le chiffre d'affaires généré pour chaque départ. Elle relie les tables CIRCUITS, AEROPORTS_DEP, MAJORATION et RESERVER afin d'associer chaque réservation à son circuit, son aéroport et sa date de départ. La clause GROUP BY regroupe les données par départ unique (circuit, aéroport et date). 


Pour chaque groupe, SUM(R.NbPers) calcule le nombre des voyageurs, tandis que SUM(R.NbPers * (CI.PrixBase + M.MontantMaj)) calcule le chiffre d'affaires total du depart. Enfin, ORDER BY ChiffreAffaires DESC classe les résultats pour faire ressortir les départs générant le plus de chiffre d'affaires en premier. 


Pour vérifier les résultats, on constate dans RESERVER que le circuit  “Rome, Florence et Venise”, au départ de Lyon le 18/10/2025, possède 11 réservations pour un total de 32 voyageurs. Dans CIRCUITS, son prix de base est de 980 €, auquel s'ajoute une majoration de 40 € dans MAJORATION. On obtient donc 32 × (980 + 40) = 32 640 €, ce qui correspond au chiffre d'affaires calculé pour ce départ.

2.3. Requêtes d’extraction


Nos requêtes d’extraction recensent les données sources nécessaires pour les sujets d’analyse dans la base de données.


Nous avons choisi de créer plusieurs requêtes d’extraction afin d’éviter les doublons dans nos données et pour que ces dernières soient cohérentes dans la représentation visuelle.


2.3.1. Requête d'extraction - TABLE_PRINCIPALE


Objectif : récupérer les informations commerciales des réservations pour calculer le chiffre d'affaires, le panier moyen, le nombre de voyageurs et les statistiques par pays et par aéroport.


CREATE TABLE TABLE_PRINCIPALE AS
SELECT c.CodeCI, c.NomCI,
       r.CodeC, r.CodeA, ad.NomA,
       r.DateDepartR AS DateDepartCI,
       r.DateResa AS DateReservationCI,
       r.NbPers,
       c.PrixBase, m.MontantMaj,
       p.CodeP, p.NomP,
       r.NbPers * (c.PrixBase + m.MontantMaj) AS CACI,
       c.NbPersMax,
       mo.CodeMois, mo.LibelleMois,
       av.TempMin, av.TempMax,
       av.TempMinMoy, av.TempMaxMoy, av.AvisMens,
       ac.DateDepartA, g.NomG, g.PrenomG
FROM CIRCUITS c, RESERVER r,
     AEROPORTS_DEP ad, MAJORATION m,
     AVIS av, MOIS mo, ACCOMPAGNER ac, GUIDES g,
     (SELECT DISTINCT s.CodeCI, p.CodeP, p.NomP
      FROM SITUER s, PAYS p
      WHERE s.CodeP = p.CodeP) p
WHERE c.CodeCI = r.CodeCI
AND r.CodeA = ad.CodeA
AND m.CodeCI = r.CodeCI
AND m.CodeA = r.CodeA
AND m.DateDepartM = r.DateDepartR
AND p.CodeCI = c.CodeCI
AND p.CodeP = av.CodeP
AND mo.CodeMois = av.CodeMois
AND mo.CodeMois = EXTRACT(MONTH FROM r.DateDepartR)
AND ac.DateDepartA = r.DateDepartR
AND c.CodeCI = ac.CodeCI
AND ac.CodeG = g.CodeG;


Résultats : 800 réservations, 2 163 voyageurs et 1 879 485 € de chiffre d'affaires.


2.3.2. Requête d'extraction - TABLE_ZONES


Objectif : répartir le chiffre d'affaires et les voyageurs entre les zones géographiques traversées par chaque circuit, sans compter plusieurs fois les montants dans le total général.


CREATE TABLE TABLE_ZONES AS
SELECT t.NomP, z.ZoneGeo,
       SUM(t.CACI / nz.NbZones) AS CA_Reparti,
       SUM(t.NbPers / nz.NbZones) AS Voyageurs_Repartis
FROM TABLE_PRINCIPALE t, SITUER s, ZONE_GEO z,
     (SELECT CodeCI, CodeP, COUNT(*) AS NbZones
      FROM SITUER
      GROUP BY CodeCI, CodeP) nz
WHERE t.CodeCI = s.CodeCI
AND t.CodeP = s.CodeP
AND s.CodeZ = z.CodeZ
AND s.CodeCI = nz.CodeCI
AND s.CodeP = nz.CodeP
GROUP BY t.NomP, z.ZoneGeo;


Résultats : 28 combinaisons pays/zone, avec un total de 1 879 485 € de CA réparti et 2 163 voyageurs équivalents.


A savoir : 


Pour calculer le chiffre d'affaires par zone géographique, nous avons choisi de le répartir équitablement lorsqu'un circuit traverse plusieurs zones. Par exemple, si un circuit rapporte 10 000 € et traverse deux zones, chaque zone reçoit 5 000 €. Nous avons appliqué le même principe aux voyageurs. Cela peut donner des valeurs décimales, comme 2,5 voyageurs. Cette répartition reste théorique et permet d'éviter les doubles comptages.

2.3.3. Requête d'extraction - TABLE_DEPARTS


Objectif : récupérer les informations sur les départs, y compris ceux sans réservation, afin de calculer les taux de remplissage et les places disponibles dans Power BI.


CREATE TABLE TABLE_DEPARTS AS
SELECT m.CodeCI, c.NomCI,
       m.CodeA, a.NomA,
       m.DateDepartM AS DateDepart,
       c.NbPersMax,
       m.MontantMaj,
       COUNT(r.CodeC) AS NbReservations,
       SUM(r.NbPers) AS NbVoyageurs
FROM MAJORATION m
JOIN CIRCUITS c
  ON m.CodeCI = c.CodeCI
JOIN AEROPORTS_DEP a
  ON m.CodeA = a.CodeA
LEFT JOIN RESERVER r
  ON r.CodeCI = m.CodeCI
 AND r.CodeA = m.CodeA
 AND r.DateDepartR = m.DateDepartM
GROUP BY m.CodeCI, c.NomCI,
         m.CodeA, a.NomA,
         m.DateDepartM,
         c.NbPersMax,
         m.MontantMaj;




Résultat : 213 offres de départ, correspondant à 174 départs distincts (circuit + date), dont 21 offres sans réservation.


Importation de tables complémentaires dans Power BI  :
 
En plus des trois tables d'extraction (TABLE_PRINCIPALE, TABLE_ZONES et TABLE_DEPARTS), nous avons également importé les tables GUIDES, ACCOMPAGNER, AVIS, MOIS et PAYS depuis Oracle.

4.2. Création de la vue ANIMATIONS_H
Une vue sur la table ANIMATIONS a été créée afin d’afficher la colonne HeureDeb au format ‘HH:MM’. 


En effet, cette colonne est de type DATE et si une donnée est insérée au format ‘HH:MM’, une date par défaut lui sera attribuée. En supposant que cette colonne ne sera pas utilisée pour des calculs, elle a été transformée en chaîne de caractères. Ainsi, cette vue sera manipulée à la place de la table ANIMATIONS.


-- Vue de la table animation permettant d’afficher heuredeb au format hh:mm
CREATE VIEW ANIMATIONS_H as
SELECT CodeAN, NomAN, TypeAN, TO_CHAR(HEUREDEB, 'HH24:MI') as HeureDEB, JourSemaine, CodeH
FROM ANIMATIONS;

4.3 Création du trigger sur RESERVER


Le dictionnaire de données définit Nb Pers Max comme le nombre maximum de personnes acceptées dans un circuit. Cette règle ne pouvant pas s’exprimer par un CHECK, car elle compare NbPers (table RESERVER) à NbPersMax (table CIRCUITS), nous avons ajouté un trigger qui refuse toute réservation dépassant la capacité du circuit:


-- Interdit une réservation dont le nombre de personnes dépasse la capacité du circuit
CREATE OR REPLACE TRIGGER trg_reserver_nbpers
BEFORE INSERT OR UPDATE OF NbPers, CodeCI ON RESERVER
FOR EACH ROW
DECLARE
    -- capacité du circuit réservé
    v_nbpersmax CIRCUITS.NbPersMax%TYPE;
BEGIN
    -- On vérifie la capacité de la réservation avant
    SELECT NbPersMax
    INTO   v_nbpersmax
    FROM   CIRCUITS
    WHERE  CodeCI = :NEW.CodeCI;


    -- Si le nombre de personnes de la réservation dépasse la capacité, on annule
    IF :NEW.NbPers > v_nbpersmax THEN
        RAISE_APPLICATION_ERROR(-20001,
            'Réservation impossible : ' || :NEW.NbPers ||
            ' personnes pour une capacité de ' || v_nbpersmax);
    END IF;
END;
